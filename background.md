I’m Dominik Peters, a social choice theorist. I’d like to make a voting web app where users can start a vote and send out a link to people to take the vote.
An easy way to think about what this project involves is to realize that such a project is essentially a form maker app, almost a clone of Google Forms. In Google Forms, people add various fields with different input types (free text, radio (= single choice), checkboxes (=approval voting), ratings), and share this form with others. A voting app will combine this with easy ways to compute the winner based on respondents’ answers, using various social choice algorithms.
Most existing vote apps of this type (Pnyx, Whale, RoboVote, OpaVote, Doodle, …) are limited to making a single decision (e.g. choosing a single date, or a single winner). But often there are several issues to be voted over simultaneously (where do we go to dinner and when; electing president + vice-president + treasurer, etc.), so it makes sense to allow for several issues – which makes it essentially the same thing as a form.
A distinctive feature of our voting app will be that it will have some input types that are made for this application: yes it will have choose-one and approval (with optional min and/or max approvals), but it will also have rankings, truncated rankings, rankings with indifferences, utility assignment, star grading, other grades (like for majority judgment), simple yes/no/abstain. In addition, it will allow single-line and multi-line freetext input (name, comments, …).
Here is how I imagine the user flow for a vote creator: Go to the website, which explains what it does. There is a demo easily reached by a button (and/or embedded in the starting page) so we can see what inputs are available (and visually see what the app is for). Then the user can click “Create Vote” button or similar. This does not require a login. This brings the user to the form creator interface, which should be full featured (e.g. drag and drop to change the order of questions, easily change input types for individual questions, have a look that is close to the final result but editable, close to WYSIWYG; auto save to localstorage maybe) which also contains editable title and description (which are also metadata of the overall vote). There might also be an option to randomize option ordering. There might also be a toggle whether a question is required or optional. There could be support for “write-in candidates” or “other: […]“ – but this complicates aggregation a lot. For many things, it would probably make sense to allow markdown styling. I’m thinking especially in description fields for the form and for questions, or for text blocks that the user writes between questions.
The user should also make privacy selections: (a) everyone can see how everyone voted (b1) everyone can see the votes but not the name of the person casting it (b2) everyone can see the votes but not the name of the person casting it, but can see an unordered list of names of those who have votes (c) votes are not visible. By standard there should be one privacy setting for the entire form, but the user should be able to go to a mode where he can choose different options for individual questions. Note that (a) and (b2) only makes sense if there is a special name field in the form (as opposed to a non-special free text input question). There is also another distinction whether votes are visible during the vote or only after the admin goes to results mode. 
After finishing making the form, the user will want to share it. The standard way would be to (A) get a link (with a random alphanumeric identifier in it) to share, such that everyone who has the link can vote. But there should be other ways, and we may add additional ones later on. I can think of: (B) just like (A) but also set a password that users must enter to access the vote, (C) generate a list of one-time-use access tokens to be handed out to voters (D) give a list of email addresses and send vote invites to them, with a link that allows voting once. Options like (D) would need to be reserved for logged-in users since sending emails incurs costs. One could also do (A) but require that users be logged in to the vote website. The standard option (A) will not be able to prevent double-voting, essentially intentionally (several voters might share the same machine).
For non-logged in creators, we will generate an admin link (with an additional random alphanumeric identifier). But we will encourage them to make an account or login. Logged-in users should have access to a dashboard showing all the votes they made and participated in. Users that make a new account at the end of the vote-make flow will have that vote added to their account.
Changes to the form: A tricky thing to decide is what changes are possible to the vote after publishing the form and receiving the first vote. Some things are easy to change (title, description, question text). But what about candidate/option names? Probably will want to allow changing those too. So votes should not be stored as “Alice > Bob > Charlie” but “cid 1 > cid 2 > cid 3” where cid refer to database IDs whose label can later be changed. Also need to consider what happens when changing privacy and sharing settings.
Editing/deleting others’ votes: This is another choice to be made, probably when the creator chooses his sharing option. On doodle, for example, everyone can edit everyone’s vote. This is useful because voters aren’t logged in, so to change your own vote, you need to be able to change everyone’s vote. For low-stakes votes that makes sense. But the admin should be able to turn it off. Maybe the admin should even be able to “throw away the key” and disallow themselves from editing/deleting votes for high-stakes votes.
From the voter’s perspective, they follow the vote link, fill out the form, and submit. On forms with visibility of others’ votes we’ll need to decide how this is displayed. There should be convenience features like localstorage/server-side saving of partial fill-in progress. After submission, there might also be a current-results page, depending on privacy settings. If the admin has closed the vote, the vote link would go directly to results (if public).
A vote admin would be able to close the vote, and then choose how results are presented. In particular, raw vote data can be displayed (e.g. an approval matrix like on Doodle), but also they can choose to present the outcomes computed by one or more voting rules (e.g. Borda, Schulze, Approval Voting, committee voting rules, and more). This will be another “builder” interface where the results page can be designed to some extent by choosing what will be displayed. But there should be shortcuts/defaults for making a “standard” results page. There should also be export options, including in Preflib format. 
Architecturally, I’d like to separate frontend and backend, with communication via http API via fetch. The backend should be PHP for easy webhosting, together with a database. For the database, I’d like it to support both sqlite and mysql. For the frontend, my preference is vanilla HTML + js, but probably it will be single-page (or few pages). For making links to the vote, we can use mod_rewrite.
We’ll want good practices everywhere, like input sanitization and “report” buttons for users to flag illegal/unpleasant content. We’ll need Terms of Service, and GDPR-compliant privacy handling (I’m based in France, server probably in Germany), including pre-building options to export data and delete data. Probably vote admins could optionally activate auto-delete, but by standard votes would persist. I’d also like a button/toggle to allow admins to “donate the vote to voting research” – allowing the anonymized votes to be studied by social choice theorists. Probably need another word than donate of course. If activated, voters would be told before submission.
